# 不分仓拼箱：业务逻辑与流程逻辑

> 模块：`apps/pinxiang_bot`  
> 入口：物流部机器人菜单 **3. 不分仓拼箱**  
> 代码真值：`packing.py` / `amazon_packaging.py` / `handler.py` / `logistics_bot/router.py`  
> 文档与实现冲突时以代码为准。

---

## 1. 业务目标

对**不分仓**发货场景：根据发货单中的装箱信息，识别**非整箱** SKU，自动给出改箱/拆分方案（件数、箱数、单箱毛重、长宽高），经物流审核后转运营；运营上传亚马逊卖家平台下载的「包装箱包装信息」表，机器人按拼箱结果填入每箱数量与箱规并回传。

**不做：**

- 不填写 Send to Amazon 的 Manifest（`ManifestFileUpload_…MPL2.xlsx`，创建货件用）
- 装箱表文件只回传运营；物流收「运营已完成」文本通知（不抄送文件）
- 不强制挂载共享盘；主数据走本地/同步目录 `files/`

**与 `dingtalk-lcl-bot` 的关系：** 交互形态类似（物流 → 运营填表），**拼箱算法独立**，不共用其分组拼箱逻辑。

## 3. 端到端流程逻辑

```text
┌─────────────┐
│ 用户回「3」  │ 进入不分仓拼箱分支（落盘 selected=pinxiang，重启不丢）
└──────┬──────┘
       ▼
┌─────────────────┐
│ 物流上传发货单   │ .xlsx，需含 sheet「装箱信息」「发货单详情」
└──────┬──────────┘
       ▼
┌─────────────────┐
│ 计算拼箱        │ 读产品信息表（可选）+ 发货单 → 拼箱结果表
│ 回传物流        │ 仅含「需处理」行；私聊发文件
└──────┬──────────┘
       ▼
┌─────────────────┐
│ 物流审核        │
│  取消 → 结束    │
│  确认 → 选运营  │ 1 / 2 或姓名
└──────┬──────────┘
       ▼
┌─────────────────┐
│ 转发运营        │ 私聊运营：说明 + 拼箱结果文件
│                 │ 内存登记 pending_ops[运营id]
└──────┬──────────┘
       ▼
┌─────────────────┐
│ 运营上传装箱表   │ 须含工作表「包装箱包装信息」
└──────┬──────────┘
       ▼
┌─────────────────┐
│ 按拼箱结果填表   │ 箱列数量 + 箱重(lb)/尺寸(in)
│ 回传运营        │ 文件名与上传时一致
│ 通知物流        │ 文本：运营已完成（不附文件）
└─────────────────┘
```

### 3.1 钉钉交互文案要点

| 阶段 | 用户动作 | 机器人行为 |
|------|----------|------------|
| 进入 | 回 `3` | 提示上传发货单 |
| 发货单 | 上传 xlsx | 回拼箱结果 + 请确认/取消 |
| 审核 | `确认` | 列出运营菜单 |
| 选人 | `1` / `2` / 姓名 | 转发给对应运营；该运营已有待办则拒绝并请改选 |
| 放弃 | `取消` | 清状态 |
| 运营 | 上传装箱表 | 填写后回传运营；同时文本通知物流已完成 |

### 3.2 路由（`logistics_bot/router.py`）

- 全局菜单：`1` CP / `2` 拆分 / `3` 拼箱 / `重置` 清分支。
- **拼箱进行中**（`pinxiang_handler.has_pending(user)` 为真）时，**优先进 pinxiang**，避免回复运营序号 `1` 被当成「1. 发货单核对」。
- 已选 `pinxiang` 分支时，后续消息留在拼箱。
- 运营有待办时无需再回 `3`，直接上传即可进拼箱处理。

### 3.3 状态

| 结构 | 存储 | Key | 含义 |
|------|------|-----|------|
| 分支选择 | 落盘 `apps/logistics_bot/.state/selected_branch.json` | userId | `cp` / `split` / `pinxiang` |
| `_pending_logistics` | 内存 + 落盘 `pinxiang .bot-workspace/pending_state.json` | 物流 userId | 已有拼箱结果；`stage=confirm` 或 `select_ops` |
| `_pending_ops` | 同上 | 运营 userId | 已转发，等待装箱表（**每运营最多 1 单**，再转会拒绝不覆盖） |
| TTL（pending） | 默认 600s | | `PINXIANG_PENDING_TTL_SEC`；加载时丢弃过期或文件已删的任务 |

`重置`（路由层）会清分支落盘并调用 `clear_user`，丢掉该用户拼箱待办。  
进程重启 / `deploy` recreate 后，仍会从 `pending_state.json` 恢复未过期且文件仍在的任务。

## 4. 业务数据输入

### 4.1 发货单（用户上传）

| Sheet | 用途 |
|-------|------|
| **装箱信息** | SKU、发货数量、单箱数量、箱子毛重(kg)、长宽高(cm) 等 |
| **发货单详情** | 发货仓库、MSKU、品名、发货量（合并单元格需向下填充理解） |

仓库以「发货仓库（单据）」为准；**不同仓库的 SKU 不互拼**（当前算法按行独立处理，未做跨 SKU 合箱）。

### 4.2 产品信息单证专用（可选主数据）

| 路径（约定） | 说明 |
|--------------|------|
| 宿主机 `files/产品信息单证专用.xlsx` | 同步脚本落地，**不进 git** |
| 容器 `/app/files/产品信息单证专用.xlsx` | compose 挂载 |

读取列（兼容 `*SKU`、外箱规格长/宽/高(cm)、单箱重量(kg)、单箱数量(pcs) 等）。  
查找顺序：发货 SKU → MSKU。  
**文件缺失时不阻断**：退回用发货单装箱信息字段。

地址簿 `files/全站点地址.xlsx` 给 CP 用，拼箱不依赖。

## 5. 拼箱业务算法（`packing.py`）

### 5.0 箱规硬约束

| 代号 | 规则 |
|------|------|
| A | 单箱毛重目标 **1～18 kg** |
| B | **非原箱规**时，长/宽/高单边 **15～60 cm** |
| C | 单箱体积 **&lt; 10000 cm³** → 长=宽=高=**20** |

**原箱规**：产品/发货单标准「一箱几件、多重、多大」，整箱不改。  
**非原箱规**：零头/不足一箱/合箱/借箱后重新定件数与尺寸。

### 5.1 箱数比 \( r = \text{发货数量}/\text{单箱数量} \)

| \( r \) | 类别 | 处理 | 进拼箱结果表 |
|---------|------|------|----------------|
| 整数且 \(r\ge 1\) | 原箱 | 整票原箱规 | **否**（仅 all_rows） |
| \(0&lt;r&lt;1\) | **B** 毛重 1～18 | 1 箱，件数=发货数量；毛重/体积=单品×件数；尺寸非原箱规 | 是 |
| \(0&lt;r&lt;1\) | **A** 毛重 &lt;1 | 同仓库多个轻货 **合 1 箱**，合计尽量 1～18kg；尺寸：优先 20×20 推高 | 是（多行同 box_group） |
| \(r&gt;1\) 非整数 | **C**（优先） | **先**算整票拼 1 箱毛重；若 1～18kg → 1 箱非原箱规（件数=发货数量） | 是 |
| \(r&gt;1\) 非整数 | **D**（C 不满足时） | 整数箱=原箱规；余数=1 箱非原箱规（同 A/B） | 是 |
| D 余数毛重 &lt;1 | 借箱 | 从同 SKU 整数箱拿出 1 箱与余数合并为 1 箱非原箱规 | 是 |

单品量：

\[
\text{单品毛重}=\frac{\text{单箱重量}}{\text{原单箱数量}},\quad
\text{单品体积}=\frac{L\cdot W\cdot H}{\text{原单箱数量}}
\]

非原箱规尺寸：体积&lt;10000→20³；否则长=宽=20，高=体积/400，高越界则调整底边，夹在 15～60。

不同**发货仓库**不得合箱。

示例：

- `801905N` 20/40（约 8.75kg）→ B 单装 1 箱  
- `801621` 47/40（整票约 17.7kg）→ **C** 整票拼 1 箱（不拆 40+7）  
- `80376351F1` 235/60（整票约 68kg &gt;18）→ D：3×原箱 60 + 余数 55 改箱  
- 两 SKU 各极轻且同仓 → A 多 SKU 合箱（结果表多行、相同箱规与总毛重）

### 5.2 拼箱结果表

**只输出需处理行**，列：

```text
发货仓库 | SKU | 发货数量 | 单箱数量 | 箱数 | 单箱毛重 | 长 | 宽 | 高
```

单位：毛重 kg（结果表保留 2 位小数），尺寸 cm（1 位）。合箱时各 SKU 各占一行，箱规/总重相同。

**文件名**（钉钉回传 / CLI 输出）：

```text
SP260708017 SP260708016 SP260708015 拼箱数据.xlsx
```

- 发货单号从发货单「装箱信息 / 发货单详情」去重后按出现顺序拼接，中间用空格。
- 若读不到任何发货单号，回退为 `{原上传文件名} 拼箱数据`。

## 6. 亚马逊装箱表填写（`amazon_packaging.py`）

### 6.1 运营上传文件要求

- 格式：`.xlsx`
- 必须含工作表：**包装箱包装信息**
- 表内已有亚马逊下发的 SKU 行、预计数量、ASIN/FNSKU 等（机器人不生成壳子）

### 6.2 填写逻辑

1. 将拼箱结果每一行按「箱数」**展开为多个包装箱**  
   - 例：180/60/3 → 3 个箱，每箱 60 件  
   - 55/55/1 → 1 个箱 55 件  
2. 从第 13 列起写「包装箱 n 数量」  
3. 更新包装箱总数、箱名 `P1 - Bn`  
4. 写箱重（**磅**）、宽/长/高（**英寸**）：  
   - kg × 2.20462 → lb  
   - cm × 0.393701 → in  
5. SKU 匹配：表内 SKU 与拼箱 SKU/MSKU 精确或前缀匹配（如 `801905` ↔ `801905N`）  
6. 「装箱数量」列按各箱合计回填  

### 6.3 回传

- 装箱表文件只发给**上传装箱表的运营**，**文件名与上传完全一致**
- 物流另收完成通知（运营名 + 拼箱结果文件名），不附装箱表

## 9. 已知边界与后续可选项

| 项 | 现状 |
|----|------|
| 多 SKU 合装一箱 | 已做：同仓且单箱预估毛重&lt;1kg 时贪心合箱（1～18kg） |
| 物流白名单 | 未做（任何用户可当物流） |
| 状态持久化 | 仅内存，重启丢失 |
| 钉盘 | 不使用，直接私聊发文件 |
| 人工尺寸/毛重 | 自动公式可能与手工表有偏差 |
| 毛重&gt;18kg | 告警后仍单箱输出，不自动拆多箱 |
